## 1. 被静默丢失或弱化的 brief 承诺（承接断裂）

### G1 · [HIGH] 业务里程碑 M1 / M2 / M3 在 PRD 中近乎消失

**brief 原文**（§业务里程碑）：
> - **M1 · V1 上线** — alex 自己能日常使用、不会再丢东西
> - **M2 · 累计 50+ 条目** — 从时间线能明显感受到自己思维演进
> - **M3 · 三个月稳定运行** — 决定是否继续迭代（加搜索/标签/同步），还是它已经够用、保持简单即可

brief 明确强调"按范式文档要求，里程碑是**业务里程碑**而非功能交付里程碑"——这是 brief 主动突出的方法论选择。

**PRD 现状**：M1 仅在 NFR-3 数据持久条款里以"brief §M1 业务里程碑"被引用一次；M2（"累计 50+ 条目 / 思维演进"）**完全未出现**；M3 仅在 §8.3 Counter-metrics 的 SM-C3 里被"呼应"。

**问题**：业务里程碑是 brief 中一个被刻意凸显的章节，承担"什么时候该判断这个产品是否还要继续做"的决策框架，PRD 没有任何专门承接位置（既不在 §7 MVP 范围、也不在 §8 成功指标），下游 Epic/Story 阶段很可能完全感受不到 M1/M2/M3 的存在。

**建议**：在 §8 成功指标后或 §7 之后增设 "里程碑" 小节，显式承接 M1/M2/M3，并把 SM 指标与对应里程碑挂钩（SM-2/SM-3 → M1；SM-1 → M2/M3）。

### G2 · [HIGH] "画廊式翻看"（gallery-style browsing）的体验承诺被弱化

**brief 原文**（§问题 3）：
> .html 的渲染门槛 — 不同于 .md 的纯文本浏览，HTML 必须经浏览器渲染才能体现原貌；Finder 双击预览体验破碎，**不支持"画廊式翻看"**

"画廊式翻看"是 brief 用来定义"为什么现有方案都不够"的关键体感词——把 .html 当成视觉作品逐一翻阅，像逛画廊。

**PRD 现状**：PRD §4.2 选择了"卡片网格 + HTML 缩略预览"这个形态，方向是对的；但 PRD 全文**完全没用到"画廊"这个词或类似的情感词**，所有描述都退化为"卡片网格"（FR-4）+ "顺序导航"（FR-5）这种功能性表述。

**问题**："画廊式"是 brief 锚定的体验隐喻——它暗示"视觉为主、轻文字、可漫游、可驻足、可翻页"。PRD 把这个隐喻拆成了 FR-4 的网格 + FR-5 的上一条/下一条，机制上覆盖了，**但隐喻本身的引导力消失了**。UX 阶段拿到 PRD 时只会看到"卡片网格 + 顺序导航"两个组件，不会自然想到"画廊感"——结果可能是设计出一个像 Google Drive 缩略图列表那样的界面，机制全对，但完全不是"画廊"。

**建议**：在 §4.2 描述段或 §1 愿景中保留"画廊式翻看"的措辞，作为 UX 阶段必须传达的体验隐喻锚点。

### G3 · [MEDIUM] "最简私有认证"的"最简"被悄悄放大

**brief 原文**（§范围 / V1 硬约束）：
> 仅 alex 一人使用：**可有最简私有认证**，无注册流程、无社交

brief 的措辞是"**可有最简**"——隐含"够用就行、不要 over-engineer"的态度。

**PRD 现状**：
- FR-6 测试性后果列出 4 条
- NFR-2 列出"三层隔离"（应用层 + API 层 + 资源层）+ 凭据隔离 + 资源层防直链外泄
- A6 假设 30 天会话
- addendum §2.3 列出 4 种候选机制

**问题**：单看每条都合理（沙箱化和资源保护确实是 untrusted HTML 项目应做的），但**整体气质**已从"最简"演变为"严肃的私有安全控制"。三层隔离的措辞读起来更像是 SaaS 产品的认证设计，而不是"hobby 单用户的最简认证"。NFR-2 资源层的"链接外泄即数据外泄"防护描述尤其"重"——这是合理的安全考虑，但 brief 的态度是"最简"。

**建议**：保留 NFR-2 的三层隔离条款（确实必要），但在描述段开头**显式承接** brief 的"最简"措辞，让下游知道这些是"必要的最简"而不是"完整的私有访问控制系统"。可加一句类似："本节是 brief '可有最简私有认证' 在面对 untrusted HTML 渲染时不得不展开的最小集合"。

### G4 · [MEDIUM] brief 中"诚实地说：这不是为商业差异化设计的产品"的态度被剥离

**brief 原文**（§差异化）：
> 诚实地说：**这不是为商业差异化设计的产品**——市场上已有大量替代品（GitHub Pages、Notion、tiiny.host 等），任何一个都能勉强满足表层需求。
> 它的存在仅基于两个主观但真实的诉求：数据所有权 + 自研历练。

这是 brief 的一个**自我校准**——主动放下"做出独特产品"的野心，明确"够用 + 我自己掌控"才是目的。

**PRD 现状**：§1 愿景承接了"借助 AI 从前端向全栈转型的第一个真实项目"和"无需商业差异化也值得存在"，承接是有的——但 brief 那种"我承认市场上有大量替代品 / 任何一个都能勉强满足"的**坦白态度**消失了。

**问题**：下游 Epic/Story 阶段（特别是 dev 阶段）拿到 PRD 时，缺少这个"主动承认替代品存在 / 这是 alex 的私人选择 / 不必试图压倒 Notion"的态度锚点，可能会在权衡时不自觉地引入"是否能比 Notion 更好"的隐性比较。

**建议**：在 §1 愿景或 §6 Non-Goals 加一句承接 brief 的坦白态度，例如"本产品不与 Notion / tiiny.host / GitHub Pages 做功能或体验上的竞争性比较——它存在的依据是 alex 的数据所有权偏好 + 自研历练目标"。

## 2. 被 FR 结构吞掉的定性表达（tone / vibe / feel）

### G5 · [CRITICAL] "提升思维逻辑"这个核心动机的情感性被结构吞没

**brief 原文**（多处反复出现）：
> - 概要："让 alex 已经在做且确认能'提升思维逻辑'的'回看自己旧产物'这个行为变得可持续"
> - 用户："已经有定期回看旧产物的习惯，且明确感到这件事'对思维逻辑是一种提升'"
> - 愿景（5 年视角）："沉淀了 alex 多年的 HTML 思维产物，**从中能直观回看自己每一阶段的思维变化——这本身就是工具最大的价值，也是这个项目最初设立的初心**"

"提升思维逻辑"是 brief 反复强调的**核心动机**——这个产品存在的根本理由不是"避免丢失"，而是"看到自己思维的变化"。brief 把它放在五年愿景的最后，措辞强烈："**这本身就是工具最大的价值，也是这个项目最初设立的初心**"。

**PRD 现状**：
- §1 愿景承接了"提升思维逻辑"和"五年视角下沉淀多年思维形态的可回溯档案"——这一段是承接的
- §2.1 JTBD"认知性"项写了"把'我的思维在变化'从模糊感觉变成可观察的事实"——承接
- **但 §4 Features 全部 7 个 FR 中，没有任何一个 FR 把"思维演进回看"作为它的核心服务对象**：
  - FR-4 时间线是"找回 + 顺序回看"——但 UJ-3"顺序回看思维演进"在 FR-4 的测试性后果里没有任何具体设计承接（没有任何条款是"让 alex 能体验到思维演进感"的——卡片网格、月份分隔条都是结构化展示，不是"演进感"的设计）
  - FR-5 完整渲染提供"上一条/下一条"导航——但"思维演进"被压缩成了"按序点击下一条"

**问题**：brief 反复强调的产品**初心**（"看到自己思维变化"），在 PRD 里只在愿景段被引用，**在 FR 层面没有任何具体的设计承诺承接它**。UX 阶段拿到 PRD 时会按 FR-4 / FR-5 设计出一个"找回 + 浏览"的工具，但"演进感"这个产品的灵魂没有被结构化为可设计的对象。

具体丢失的设计契机：
- 月份分隔条（FR-4 已有）是"演进感"的天然载体——但 PRD 只把它定义为"视觉分隔条，无折叠"，没有提到它的语义角色（让 alex 看到"我在 2026 年 3 月做了什么，在 2026 年 5 月做了什么"的对比感）
- 顺序导航（FR-5）的方向跟随时间线排序——但没有任何条款承诺"在顺序浏览时让 alex 感受到思维变化"（如显示当前位置在时间线上的相对位置、距上一条的时间间隔等）

**建议**：在 §4.2 描述段显式标注"时间线不仅是找回工具，也是 alex 感受思维演进的视觉载体"，在 FR-4 / FR-5 至少加一条测试性后果（如"显示当前 Entry 与上一条的归档时间间隔"或"月份分隔条的视觉密度反映 alex 在那个月份的产出强度"）来把"演进感"落到可设计的具体行为上。

**严重度依据**：这是 brief 中**最强烈、最反复**强调的产品初心，但在 PRD 中**没有任何 FR 层面的设计承诺**承接它。这不是措辞 / 隐喻丢失，是**核心动机在 FR 层的结构性缺席**。

### G6 · [MEDIUM] "实战载体 / 历练"的工具感被减弱

**brief 原文**（多处）：
> - 概要："这同时也是 alex 借助 AI 完成前端→全栈能力闭环的第一个真实项目——**既是工具，也是历练**"
> - 用户："前端工程师，正借助 AI 向全栈转型"
> - 差异化："**自研历练** — 这是 alex 从前端转全栈的第一个真实项目，要借助 AI 完整跑一遍 BMAD 流程 + 前后端 + 部署上线的全栈实战"

brief 把"工具/历练"作为**并列的产品定位**——这不是"附带"目标，是产品存在的两大支柱之一。

**PRD 现状**：§1 愿景承接了"既是工具，也是历练"措辞；§2.1 JTBD 末尾"元层 / Builder 视角"承接了"实战载体"——承接是有的。

**但**：
- §8 成功指标的 SM-4 / SM-5 / SM-6 是"完成 BMAD 流程 / 完成全栈实战 / 不被迫重构"——这些是**产出物指标**，不是"历练"的体感指标
- brief 措辞是"**借助 AI** 完整跑一遍"——"借助 AI"在 PRD 没有任何承接，连 SM 都没有提到"借助 AI 完成的程度"
- "历练"在 PRD 中其实是一个**没有任何 FR 承接**的纯元层概念——这没问题（历练本质上不应是 FR），但 SM-4/5/6 又把它压缩成纯产出物，丢失了 brief 的"借助 AI"这个过程性强调

**建议**：在 SM-4 或 SM-6 加一条体感性的元层指标（如"3 个月使用后 alex 自评：借助 AI 完成 BMAD 流程 + 全栈实战的可复制度"）。或在 §1 愿景明确承接"借助 AI" 这三个字作为历练的核心方法论。

### G7 · [LOW] brief 中"已发生过实际丢失"的情绪重量在 PRD 中被平淡化

**brief 原文**：
> - 问题 §2："**遗忘 + 实际丢失** — 时间一长记不起来'曾经做过什么'，且**已发生**找不到的事实"
> - 概要："已发生过'想回看却找不到'的实际**损失**"

brief 用了"**实际丢失**""**已发生**""**损失**"等词，传达"这不是潜在风险，是真实发生过的痛"。

**PRD 现状**：§1 愿景写了"**已经发生过实际丢失**"——承接是有的，措辞也保留了。§2.1 JTBD"情绪性"项"消除'我做过但找不到了'的焦虑——已经发生过的实际丢失不再重演"——也承接了。

**问题**：承接虽在，但**重量被分散**——brief 把它放在问题列表的前两条里反复强调（"概要"+"问题"两处），是产品立项的**触发性事件**；PRD 把它放在愿景段中间一句，作为"已经在做但难以维持"的背景，**情绪密度降低了**。

**严重度低**：这更多是质感差异，不是结构性缺失。alex 自己读得到。

## 3. PRD 超出 brief 未说明的 scope creep

### G8 · [MEDIUM] FR-7 "下载原 .html" 在 brief 中无依据

**brief 现状**：brief §范围 / V1 必须有列出 4 条：上传、时间线、点击渲染、云部署。**没有提到下载**。brief §范围 / V1 暂不做也未列"下载"——属未表态。

**PRD 现状**：FR-7 把"下载原 .html"作为 V1 in scope 的管理动作，理由是"承担'数据所有权'承诺的兜底——alex 任何时刻都能把单条 Entry 取回本地"。

**问题**：这是**正向 scope creep**——PRD 主动增加了 brief 未涵盖的功能。从"数据所有权"立场推导出"应该能下载"是合理的，但 brief 没有明示"V1 必须能下载单条"。PRD 应该至少标注"此项为 PRD 从 brief 数据所有权立场推导出的新增 V1 项，brief 未明示"。

**建议**：在 FR-7 "下载原 .html"条款下加注释（类似 ASSUMPTION 风格），说明这是 PRD 从 brief 数据所有权立场推导新增、brief 未明示的 V1 项；或在 §0 文档目的的"承接关系"段落末尾，集中列出 PRD 相对 brief 的新增项。

### G9 · [LOW] FR-4 "排序切换" 在 brief 中无依据

**PRD 现状**：FR-4 加入"alex 可在'最新在前 / 最早在前'之间切换"，并在 OQ-5 承认"V1 不持久化偏好"。

**问题**：这是合理的小扩展（正序切换对"思维演进顺序回看"确实有用），但 brief 没明示，PRD 也没在引入时标注"超出 brief"。

**严重度低**：这是合理扩展，不需要回退，但应该被记入"PRD 相对 brief 的新增项"清单以便下游 trace。

## 6. 建议优先处理顺序

按"对下游 UX / 架构 / Epic 阶段影响"排序：

1. **G5（critical）**：核心动机"思维演进回看"在 FR 层缺席——下游 UX 阶段会受影响，必须修
2. **G1（high）**：业务里程碑 M1/M2/M3 没有专门承接位置——影响项目何时判断"够用 / 该收手"的决策
3. **G2（high）**："画廊式翻看"隐喻丢失——UX 阶段的视觉方向锚点缺失
4. **G3（medium）**："最简"认证态度被放大——下游可能 over-engineer 认证
5. **G6（medium）**：历练的"借助 AI" 过程性弱化——元层指标可补
6. **G8（medium）**：下载功能未标注 scope creep
7. **G4（medium）**：坦白态度剥离
8. **G7（low）**：丢失情绪重量被平淡化
9. **G9（low）**：正序切换未标注 scope creep

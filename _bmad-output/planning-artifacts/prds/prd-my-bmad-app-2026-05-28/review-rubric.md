# PRD 质量审阅 — MindPrint（个人 HTML 思维档案库）

> 校准基准：**hobby / 单用户 / ~2 页 rigor**。本审阅按此基准给出判断——不强加企业级严苛度，但**实质性内容的标准不打折**(substance bar 不让步)。

## 总体裁决（Overall verdict）

**这是一份高于其 hobby 校准基准的 PRD。** 它最强的地方在 §3 Glossary 严格约束术语 / §4 FRs 都附"测试性后果" / §8 配 Counter-metrics 制衡 Primary SMs / §6 与 §9 把"不做"和"未决"显式摆出。**整体可直接进入 UX 与架构阶段**。最大的暗礁是 §4.2 FR-4 中的"HTML 内容缩略预览" + NFR-1 沙箱化 + A5 三者形成的**复合假设**——目前 PRD 把架构复杂度向 addendum §2.4 抛接得太干净，缩略预览到底是否还在 hobby 复杂度内、能否兼容"NFR-1 沙箱化"，是下游第一个就会撞上的真实风险，PRD 没在 §9 Open Questions 立项。其他个别问题（OQ-7 标"OQ 中最高"但仍留在 V1 之外、SM-1/-3 验收依据偏弱）是次要的。

---

## 1. Decision-readiness — **adequate**

PRD 的关键决策点几乎都**作为决策被陈述**，而非藏在"考量"中。例如：

- §4.1 FR-1 "V1 仅接受单文件——多选 / 拖入多个文件触发明确"V1 仅支持单文件"提示"——这是一个被选定的决策，不是开放选项。
- §4.4 FR-7 "永久删除（硬删除，无垃圾桶）"——明确选择了 OQ-2 中两种语义之一，并把另一种（Unarchive 回到本地下载文件夹）显式留到 OQ-2。
- §7.2 把"标签 / 搜索 / 自动从 Downloads 同步 / 批量上传"提出来作为"最容易冲动加但必须坚定不做的三条"——这是真的有立场，不是中性表述。
- §8.3 Counter-metrics 显式说 "**不优化"打开频次"** —— MindPrint **不应**通过推送 / 邮件提醒 / 红点 / 通知等机制刺激 alex 打开应用" —— 这是一段有锐度的反向决策，不是 PRD 模板套话。

**但有 3 处把决策包装成"留给架构"——只在风险与 hobby 校准之间擦边而过，未触发"broken"但值得点名**：

- **§4.2 FR-4 "卡片视觉主体——HTML 内容缩略预览"**：PRD 选择了一个**很高体验上限**的能力（"视觉上能辨识原 HTML 大致长什么样"），同时通过 A5 + addendum §2.4 把生成机制完全留给架构。addendum §2.4 自己已指出方案 b（服务端截图）"在 hobby 复杂度内复杂度过重"，方案 c 体验不达标——也就是说**方案 a（缩放 iframe + 视口懒渲染）已经被默认锁定，但 PRD 主文档没承认这一点**。这是把决策夹在 addendum 里。
- **OQ-7 全量导出**："**优先级建议：OQ 中最高——数据所有权是 brief 立场的核心**" — PRD 自己承认这是 OQ 中最高、且 brief 立场要求承接，**但仍把它留在 V1 之外**。这个张力没被显式抬起来：要么承认 V1 不完全兑现 brief 的"数据所有权"承诺、要么 V1 加最简全量导出。目前 PRD 是"承认了张力但不解决"，没有 `[NOTE FOR PM]` 把张力本身钉住。
- **OQ-2 删除语义**：FR-7 已选硬删除并明确告诉 alex "无法恢复"，OQ-2 说"v2 是否加'撤销归档（取回到本地）'语义"——但 FR-7 已经有"下载原 .html"动作，"删除 + 先下载"的组合在功能上**已经能模拟 Unarchive**。这让 OQ-2 显得有点"修辞性开放问题"。

### Findings
- **medium · 缩略预览的决策夹在 addendum** (§4.2 FR-4 + A5 + addendum §2.4)。PRD 主文档说"由架构决定"，但 addendum §2.4 已把方案 b/c 排除并暗示"先评估方案 a"。这把一个 hobby 项目里**最重的架构复杂度决策**包装成开放——下游架构看完 PRD 会以为还有余地，看完 addendum 才发现已经几乎选定。*Fix*：要么把 §9 加 OQ-8 "卡片缩略预览机制选择 — 影响沙箱化方案 + 浏览端性能 + 整体复杂度"，要么在 A5 里直接补一句"PRD 倾向缩放 iframe + 视口懒渲染，最终架构决定"。
- **medium · OQ-7 是 brief 立场缺口而非普通 Open Question** (§9 OQ-7 + §6.2)。PRD 自己说"OQ 中最高"，brief §差异化把"数据所有权"列为存在理由之一，FR-7 单条下载只承接了部分。继续推到 V1 之外是一个产品立场选择——但 PRD 没把这个张力显式抬到决策层。*Fix*：在 §6.2 该条加一段"注：本项与 brief §差异化"数据所有权"立场存在张力——V1 通过 FR-7 单条下载部分承接，全量导出未做。M3 retro 时再评估是否提前到 v2"。
- **low · OQ-2 已被 FR-7 隐式解决** (§9 OQ-2 + §4.4 FR-7)。"下载原 .html + 永久删除"组合在功能上等价于 Unarchive。*Fix*：OQ-2 改写或删除——例如改成"是否需要把'下载+删除'打包成单一'撤销归档'动作"。

## 2. Substance over theater — **strong**

这是这份 PRD 最讨人喜欢的维度。**几乎没有 furniture**：

- §1 愿景的 "*MindPrint 沉淀的不仅是 .html 文件，而是 alex 多年思维形态的可回溯档案*" 是这个具体产品才能写出的话——swap 到任何同类 PRD 都不成立。这不是 vision theater。
- §2.1 JTBD 分了 functional / emotional / cognitive / 元层 四类——并不只是模板套用，**每一类都有一条切到具体场景**："消除'我做过但找不到了'的焦虑——已经发生过的实际丢失不再重演" 是 emotional 的真实承接（brief §问题里有"已发生过的事实"）。
- §2.3 非用户写"任何 alex 之外的人（包括朋友 / 同事 / 未来雇主——v1 不提供分享外链）"——把潜在的"分享给雇主看作品集"幻想显式排除，这是有立场的。
- §4 的每个 FR 都附"测试性后果"，且**这些后果是产品决策不是实现细节**——例如 FR-3 "即使渲染本身失败（HTML 损坏 / 渲染异常），归档动作仍视为成功——Entry 已入库，alex 可从时间线后续手动诊断" 是一个有趣的、显式的产品决策（渲染失败 ≠ 归档失败）。
- §5 NFRs 只纳入 3 条（沙箱化、私有访问、基本可靠性），明确写"hobby 项目最小集合"——避免了 NFR theater（"系统必须可扩展 / 安全 / 可靠"那种）。
- §8.3 Counter-metrics 是这份 PRD 的亮点——三条都不是模板话，**每条都对一个具体真实诱惑投反对票**。

**唯一一处接近"furniture"的位置**：§2.1 中的 "元层 / Builder 视角" 这一条 JTBD（"把这个产品作为前→全栈能力闭环的实战载体"）——它真实，但**它不在 §4 FRs 中驱动任何决策**。所有 §4 FR 都是给"用户 alex"用的，没有任何 FR 是为"Builder alex"设的。这条 JTBD 实际上 § 2 应该承认它**只承接到 §8.2 SM-4/-5/-6**，与 §4 是松耦合。

### Findings
- **low · Builder JTBD 不驱动 §4 FR** (§2.1 元层 + §4 + §8.2)。这条 JTBD 真实但只承接 §8.2 元层 SM，没有任何 FR 受它约束。*Fix*：§2.1 元层那一条加一句 "*此 JTBD 不驱动 §4 任何 FR，仅承接 §8.2 SM-4/-5/-6*"——这种"显式承认松耦合"反而是 substance 而非 theater 的体现。

## 3. Strategic coherence — **strong**

PRD 有一个清晰的 thesis：**"alex 已经在做'回看旧产物'这件事，但被'文件散落 / 找不到'侵蚀；MindPrint 让一件已经在做但难以维持的事变得可持续"**（§1 段 2）。这个 thesis 不是"我要做一个工具"，而是"我要给一个已经发生的行为去掉摩擦"。

整个 PRD 的特征选择能追溯回这个 thesis：

- §4.1 归档（消除"散落"）→ §4.2 时间线（消除"找不到"）→ §4.3 完整渲染（消除"Finder 双击体验破碎"）—— **每个 Feature 都对应 brief §问题里的一个具体痛点**，没有"觉得也该有所以加"的功能。
- §7.2 "最容易冲动加进 V1 但必须坚定不做的三条" 完全符合 thesis：标签 / 搜索（"50 条目以内时间线+缩略预览足够"——thesis 是"已有的回看行为"，不是"内容多到检索"）；自动同步（与"已经在做"的 thesis 不冲突，但显著加复杂度）；批量上传（"AI 产出节奏是零散单文件"——thesis 是基于真实使用节奏的，而非想象）。
- §8.1 SM-1（实际回看次数）+ SM-2（0 起新增丢失事件）+ SM-3（80% 新产出进入 MindPrint）—— **每条都直接验证 thesis 的一个面**（持续回看、不再丢、用起来），不是 DAU/MAU 那种"测量活动而非测量 thesis"。
- §8.3 Counter-metrics SM-C2 "**不优化'打开频次'**" 是 thesis 的一个直接守护——MindPrint 是"用户已经想做的事变得可持续"，不是"诱导用户产生新习惯"。

**少数让步**：§4.2 FR-4 把"HTML 内容缩略预览"作为卡片视觉主体——这条选择从 thesis 上能解释（"思维形态在浏览时直接可见"，承接 UJ-3 思维演进回看），但**它把整个项目从"小而美"推向"有点重的视觉档案产品"**。这不是 thesis 偏移，但是 thesis 的一个强解释。下游架构如果按 addendum §2.4 方案 a 落地，会发现这条决策的复杂度在 hobby 边缘擦过——但 PRD 自己**没承认**这是一个 thesis 边界决策。

### Findings
- **low · 缩略预览是 thesis 的强解释，PRD 没把它标出来** (§4.2 FR-4 描述段 + thesis §1)。 文中说"呈现形态为卡片网格——含原 HTML 的内容缩略预览，让'思维形态'在浏览时直接可见"——这条解释成立但隐含 thesis 边界。*Fix*：FR-4 描述段加半句"此决策与 §1 thesis 直接相关——若 alex 体验中觉得'内容缩略预览'未带来质变，M3 retro 应考虑降级到首屏文本摘要"。

## 4. Done-ness clarity — **adequate (偏 strong)**

这是 rubric 要求"无情判断"的维度。我从每个 FR 提取测试性后果，看是否能写出 acceptance：

| FR | 可被验收的后果 | 不可验收 / 模糊处 |
|-----|---|---|
| FR-1 上传 | 扩展名拒绝、10MB 拒绝、多文件拒绝、网络中断重试、失败事务性 | "向 alex 返回**明确**提示" — 明确的具体形态由谁判？UX 阶段补 |
| FR-2 元数据 + 标题 | 自动捕获哪些字段、`<title>` 抽取规则、fallback 规则、200 字符截断、确认/取消、时间戳不可改 | **强** |
| FR-3 归档后渲染 | ≤1 次跳转看到完整渲染、新 Entry 立即在顶、渲染失败归档仍成功、有返回导航 | "≤1 次跳转"勉强可验 |
| FR-4 时间线网格 | 多列响应式、卡片三类信息、缩略预览沙箱化、默认倒序、可切换排序、月份分隔、空状态、全量加载元数据 | "**HTML 内容缩略预览（卡片视觉主体）**" — 这一条**没有可验收形态**。"视觉上能看出原 HTML 大致长什么样"是 alex 主观判定。给 hobby 项目可以接受，但下游 dev 验收会卡这里 |
| FR-5 完整渲染 | 全屏占主区域、视觉等同于双击 .html、顶部 chrome 含 3 项、上一/下一导航、加载失败处理、响应式、沙箱化引用 NFR-1 | "**视觉上等同于**双击 .html 在浏览器打开" — 这是个非常强的承诺，但"等同"的边界（字体回退、外链资源加载行为、`<script>` 部分行为被沙箱拦截后页面如何呈现）只在沙箱化"必要副作用"一条上含糊带过 |
| FR-6 私有访问 | 未认证请求拒绝并重定向、合理会话期、多设备登录、机制留架构 | "**合理时长**" → A6 指 30 天，OK |
| FR-7 管理 | 编辑标题立即生效、时间戳不变、文件名规则、二次确认、删除不可撤销、删除清除三类资产 | "下载内容为**原归档时的完整 HTML 字节流**——MindPrint 不做后处理 / 不修改" — 是 hash 等价还是字节等价？dev 会问。 |
| NFR-1 沙箱化 | 凭据隔离 / 行为隔离 / 机制开放 | **可验收清单完整**——这是 NFR 中难得做实的一条 |
| NFR-2 私有 | 三层隔离（应用 / API / 资源）+ 401 而非 404 | **强**——"返回 401 而非 404 避免泄露 Entry 是否存在"是有 OWASP 思路的具体后果 |
| NFR-3 可靠性 | 错误隔离 / 数据持久 / 浏览器覆盖 / 响应感软目标 + 软目标承认 | 显式标"软目标 / 未达成不阻塞上线"——hobby 项目正确处理 |

**两条值得点名**：

- **FR-4 缩略预览的可验收性是这份 PRD 的最大软肋**。"视觉上能看出原 HTML 大致长什么样" 是 alex 自评，没有客观 acceptance。给 hobby 项目可以接受（alex 既是 PM 又是用户又是 dev），但**dev 实施时如果方案 a 缩放 iframe 性能不够、要降级到方案 c 文本摘要——这个决策在哪里发生？PRD 没说**。这是把"done 的定义"留给了实施过程。
- **FR-5 "视觉等同于双击 .html"** 是一个**很强**的承诺。沙箱化必然带来的差异（如 `<script>` 被禁止后页面的视觉退化、cookie/localStorage 访问失败导致样式塌）只标了一句"沙箱化必要副作用——例如尝试修改 top.location 等被阻止"。**如果 Entry HTML 含依赖 `localStorage` 主题切换 / 依赖 cookie 的 A/B 显示分支** —— 视觉就不"等同"。这条后果 PRD 留了"必要副作用"做兜底，但兜底范围没界定。

### Findings
- **high · FR-4 "HTML 内容缩略预览"无客观可验收** (§4.2 FR-4 卡片内容第二项 + A5)。"视觉上能辨识原 HTML 大致长什么样"是主观目标。下游 dev 实施时若方案 a 性能不达、降级到方案 c 文本摘要——这个决定在哪做？PRD 没给。*Fix*：把这条后果改成可验收形态——例如 "*缩略预览满足以下两条之一*：(a) iframe 缩放渲染了 Entry HTML 的前 N 像素视区；(b) 服务端预渲染的位图。**若架构阶段判定方案 a 性能不足，需触发 PM 回顾——不能静默降级到纯文本摘要**"。
- **medium · FR-5 "视觉等同于双击 .html" 的副作用边界不清** (§4.3 FR-5 原貌等同性 + NFR-1)。沙箱化必然引入视觉差异，"必要副作用"举例只有 3 个 (`top.location` / `document.cookie` / `parent.postMessage`)，未覆盖"被沙箱阻断后页面降级"的常见场景（如依赖第三方 SDK 注入 DOM 的 HTML 在沙箱下显示空白区域）。*Fix*：在 FR-5 加一条 — "*'视觉等同'排除以下场景：(a) Entry HTML 依赖 `localStorage` / `sessionStorage` / cookie 的视觉分支；(b) Entry HTML 依赖与 MindPrint 应用通信的 SDK；(c) 外链资源加载失败（参见 OQ-4）*"。或把这条作为 OQ-4 的一部分扩张。
- **low · FR-7 下载"原归档时的完整 HTML 字节流"未明确" 字节等价 vs hash 等价"** (§4.4 FR-7 下载块)。*Fix*：补一句 "下载内容**字节级别等同**于归档时上传的文件"。

## 5. Scope honesty — **strong**

这是这份 PRD 第二讨人喜欢的维度。**省略几乎都是显式的**：

- §6.1 永久边界（多用户 / 公开分享 / AI 生成 HTML / 内置编辑器）+ §6.2 V1 暂不做（12 条）+ 每个 FR 自己的"Out of Scope" + §7.2 "最容易冲动加"三条——**四层显式排除**，远超 hobby 项目最低要求。
- 7 条 `[ASSUMPTION]` 全部 inline 标注且在 §10 集中索引（A1–A7），可双向往返。
- `[NOTE FOR PM]` 出现在 5 处真实张力：去重（FR-1）、排序持久化（FR-4）、沉浸全屏（FR-5）、全量导出（FR-7 / §6.2）——都是"我现在不解决但未来 PM 视角值得复审"。
- §9 Open Questions 7 条，**每条都有"触发再评估的条件"**——这意味着 alex 给未来自己留了"什么时候该回头看这个问题"的指针，不是"我现在不想想"的免责声明。
- §7.2 "最容易冲动加进 V1 但必须坚定不做的三条"是**正面排除**——不是"也许不做"，而是"哪个最有诱惑就把哪个钉死"。

**Open-items 密度**：7 ASSUMPTIONs + 7 Open Questions + 5 `[NOTE FOR PM]` = 约 19 个未决条目，分布在 ~2 页 PRD 中。对 **绿灯放行** 的 PRD 来说算高，但对 **hobby + alex 是唯一 stakeholder** 的项目，这密度是"诚实"而非"软"——所有未决项都是 alex 自己未来会复审的，没有"等别人决定"。

**唯一软处**：§6.2 V1 暂不做有 12 条，但**没有为这 12 条标优先级**——OQ-7（全量导出）已经在 §9 标"OQ 中最高"，但 §6.2 本身没标。下游 M3 retro 时 alex 可能记不起"这 12 条里哪几条是真需要复审、哪几条是默认不做"。

### Findings
- **low · §6.2 12 条 V1 暂不做未标优先级 / 复审触发** (§6.2)。OQ-7 已在 §9 标"OQ 中最高"，但 §6.2 本身让 12 条平铺一片。*Fix*：把 §6.2 与 §9 OQ-X 编号 cross-ref——例如"全量导出 / 一键迁出 → OQ-7"，"沉浸全屏 → OQ-6"，"排序偏好持久化 → OQ-5"，"内容去重 → OQ-3"。这样 §6.2 自动获得未来复审入口。

## 6. Downstream usability — **strong**

这份 PRD 显然是为"feed UX → 架构 → epics/stories → dev"设计的（§0 文档目的明确说了）。

- §3 Glossary 是 7 个术语的强约束，且每个 FR 文本几乎严格使用这些术语——"Entry" / "Archive" / "Timeline" / "Full Render" 没看到同义词漂移（详见下文 Mechanical notes）。
- FR-1 ~ FR-7 编号连续不重复，FR-3 / FR-5 / NFR-1 等明确 cross-ref 到具体章节（§4.3 / §5 NFR-1 / addendum §2.1）—— cross-ref 都能 resolve。
